# CBQF v1 批量确定性转发测试报告

测试时间：2026-07-16  
机制：CBQF, Cyclic Batch Queue Forwarding  
版本定位：CBQF v1 稳定验证版  
配置文件：`configs/cbqf_6sw_4host.json`  

---

## 1. 测试目标

本次测试用于验证 CBQF 对批量突发 TSN 数据包的确定性转发能力。

CBQF 与前面 CSQF、TCQF、TQF 的主要区别在于：CBQF 不再只关注单个周期内单个 TSN 包的时隙匹配，而是面向一个发送批次中的多个连续数据包。其核心目标是让同一批次的数据包进入同一个批量缓冲队列，并在延迟若干时隙后统一释放，从而避免突发到达导致同一批次内部分包错过服务窗口。

本次测试重点观察：

1. 批次是否完整到达。
2. TSN 批量流的 P50、P95、P99 和尾部异常。
3. BG 流在 CBQF 保护 TSN 后的延迟表现。
4. 当前版本是否适合作为 CBQF v1 稳定原型。

---

## 2. 实验配置

| 项目 | 配置 |
|---|---|
| 拓扑 | 6 个交换机 + 4 个主机 |
| 路径 h1_h3 | h1 -> s1 -> s2 -> s5 -> s6 -> h3 |
| 路径 h2_h4 | h2 -> s1 -> s3 -> s4 -> s6 -> h4 |
| TSN 批次大小 | 5 packets / batch |
| CBQF 队列 | queue1、queue2 为 TSN batch queue，queue0 为 BG queue |
| slot_us | 8192 us |
| cycle_us | 65536 us |
| slots_per_cycle | 8 |
| release_delay_slots | 2 |
| slot_service | `[1, 2, 1, 2, 0, 2, 1, 0]` |
| BG 服务 slot | slot 4、slot 7 |
| 异常阈值 | 57344 us |

当前稳定版使用固定全局服务表：

```text
slot 0 -> queue1
slot 1 -> queue2
slot 2 -> queue1
slot 3 -> queue2
slot 4 -> queue0
slot 5 -> queue2
slot 6 -> queue1
slot 7 -> queue0
```

TSN 数据包根据 batch 标识映射到 queue1 或 queue2。同一批次内的 5 个包保持相同 batch 语义，避免被不同到达时隙拆散。

观察：

1. TSN 异常率整体约 1.41%，高于 CSQF v2 和 TCQF 默认版本，但测试负载也从单包周期发送变为 batch_size=5 的连续突发发送。
2. h1_h3 的 TSN 异常率高于 h2_h4，说明当前固定服务表在两条路径上的尾部表现仍不完全均衡。

4. TSN P95 基本稳定在 44.7-48.1 ms 区间，说明大多数 batch 包能在预期延迟窗口内完成转发。

## 6. 关键结果分析

### 6.1 CBQF 的有效性

CBQF v1 已经验证了核心设计目标：面向批量突发数据包时，同一 batch 可以保持完整转发。

本次测试中所有 TSN flow 的 batch completeness 均为 100%。这说明 batch_id 到 batch queue 的映射逻辑有效，发送端连续发出的 5 个包没有因为到达时隙差异而被拆成不完整批次。

### 6.2 延迟释放的作用

`release_delay_slots=2` 比之前 shifted-GCL 方案更加稳定。其原因是当前 P4 入队逻辑仍采用全局 batch queue 映射，而非每交换机本地 remap。固定服务表与延迟释放配合后，虽然牺牲了一部分平均时延，但能更稳定地吸收 batch 突发。

从结果看：

```text
TSN P95: 44.7 ms - 48.1 ms
Batch P95: 46.8 ms - 49.8 ms
Batch completeness: 100%
```

这说明 CBQF v1 对绝大多数批量包具备稳定缓冲和释放能力。

### 6.3 尾部异常的来源

当前仍存在 P99 和 MAX 较高的问题，尤其 h1_h3 中 FID 101、102、103 的 P99 分别达到 81.2 ms、74.9 ms、85.2 ms。

可能原因包括：

1. BMv2 是用户态交换机，线程调度容易出现周期级抖动。
2. batch_size=5 使瞬时入队压力显著高于单包机制。
3. 固定服务表没有针对不同路径做 per-switch local remap。
4. h1_h3 与 h2_h4 的中间路径不同，服务窗口相位误差可能在 h1_h3 上更明显。

这些异常不影响 batch 完整性，但会影响最坏时延保证。因此当前 CBQF v1 更适合作为稳定原型，而不是最终硬实时上界版本。

## 7. 与前序机制的关系

| 机制 | 主要目标 | 当前表现 |
|---|---|---|
| CSQF | 源路由式逐跳 slot 调度 | 单包确定性好，P95 较低，适合展示 per-hop slot stack |
| TCQF | 本地 cycle tag remap | 头部较简单，P95 稳定，但平均等待较高 |
| TQF | 基于到达时间计算输出 slot | 轻量，但对时钟和调度抖动敏感 |
| CBQF | 批量突发数据包的完整性和缓冲释放 | batch completeness 100%，适合展示批量确定性保障 |

CBQF 的定位不应和 CSQF 直接比较单包最低时延。它更适合回答这个问题：

```text
当一个周期内连续发送多个 TSN 包时，如何保证这一批包整体稳定转发，而不是因为突发到达和时隙错位导致批内部分包异常？
```

本次测试说明 CBQF v1 对这个问题已经给出了有效原型。

---

## 8. 当前版本结论

CBQF v1 稳定版可以作为当前阶段的有效结果保留。

主要结论：

1. CBQF 的 batch buffer 机制工作正常。
2. 所有 TSN batch 完整到达，完整率为 100%。
3. TSN P95 稳定在约 45-48 ms，batch P95 稳定在约 47-50 ms。
4. BG 被限制在较少服务窗口中，因此 BG 延迟和异常率高于 TSN，符合 TSN 优先保护逻辑。
5. 当前版本仍存在少量 TSN 长尾异常，主要体现在 P99 和 MAX。
6. shifted-GCL 版本不适合作为当前稳定版，因为它需要配套 per-switch local queue remap，否则会造成队列服务窗口错位。

推荐将当前版本命名为：

```text
CBQF-v1-stable
batch_size=5
release_delay_slots=2
slot_service=[1,2,1,2,0,2,1,0]
```

后续如果继续优化，可以单独设计 CBQF-v2，引入 per-switch local queue remap 或 batch-aware admission control。但对于当前论文或阶段性实验，CBQF-v1 已经能够支撑“批量确定性缓冲转发”的机制验证。
